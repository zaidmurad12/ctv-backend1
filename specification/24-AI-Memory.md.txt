# Architectural Baseline

The platform is designed around the following decisions:

- Clean Architecture
- Modular Monolith in Phase 1
- Provider-based integration model
- Core independence from external providers
- Cinemana as the only content source
- TMDB as a metadata enrichment provider only
- PostgreSQL and Prisma as the persistence foundation
- Redis and BullMQ for caching and asynchronous workers
- REST API as the main client integration contract
- Android TV and admin dashboard as client applications

---

The following constraints must remain in effect during all future work:

- Do not invent architecture.
- Do not invent API endpoints.
- Do not invent database fields.

- Follow the roadmap in order.
- Do not begin application implementation before the required foundation is in place.

## Milestone 2 Update

Status: Completed

Major deliverables completed:
- Generated the Prisma Client package from `prisma/schema.prisma` and wired `pnpm db:generate` at the root.
- Added additive `reconstitute()` factories to the Movie, TVShow, Season, and Episode domain entities so infrastructure can rehydrate aggregates from persisted state without re-running creation invariants. This was the one necessary domain change for this milestone; no existing domain behavior changed.
- Implemented a Prisma <-> domain mapping layer (`MovieMapper`, `TVShowMapper`, `SeasonMapper`, `EpisodeMapper`) under `packages/infrastructure/src/prisma/mappers`, translating Prisma rows to domain aggregates and back.
- Implemented `PrismaMovieRepository`, `PrismaTVShowRepository`, `PrismaSeasonRepository`, and `PrismaEpisodeRepository`, replacing the previous stub implementations (which always returned `null`/`[]`). Movie/TVShow reads respect soft-delete (`deletedAt: null`); Season/Episode have no soft-delete column in the schema.
- Implemented `PrismaUnitOfWork.execute()`, which runs a callback inside a single Prisma `$transaction` and hands it repository instances bound to the transactional client.
- Implemented a real Redis cache client (`RedisCacheClient`, ioredis-backed) alongside the existing in-memory cache, and a real BullMQ queue client (`BullMQQueueClient`) alongside the existing in-memory queue.
- Implemented `DatabaseHealthCheck` (`SELECT 1`) and `RedisHealthCheck` (`PING`).
- Added a dependency-injection composition root (`INFRA_TOKENS`, `registerInfrastructure`, `createInfrastructureContainer`) that registers config, logger, Prisma client, Redis connection, all four repositories, the unit of work, cache client, and health checker as singletons on the existing generic `Container`.
- Rewrote `packages/infrastructure/src/config/env.ts` to match the variables documented in `specification/18-Configuration-Reference.md.txt` exactly (`REDIS_HOST`/`PORT`/`PASSWORD`/`DB`, `QUEUE_PREFIX`/`CONCURRENCY`/`RETRY`/`TIMEOUT`, `DATABASE_POOL`/`TIMEOUT`/`LOGGING`) instead of the previous ad hoc `REDIS_URL`/`QUEUE_NAME` shape; updated `.env.example` to match.

- Wired a `test` task into `turbo.json`, a `test`/`db:generate` script into the root `package.json`, and a Prisma-generate + test step into the GitHub Actions CI workflow.
- Fixed a repo-wide ESLint bug: the core `no-unused-vars` rule (from `js.configs.recommended`) was flagging TypeScript-only constructs (interface method parameters, constructor parameter properties) as unused across every package; it is now disabled in favor of `@typescript-eslint/no-unused-vars` only. This was latent before because no package other than the new infrastructure work exercised `pnpm lint` against files using those constructs.
- Fixed `packages/infrastructure/tsconfig.json`: it previously path-mapped `@ctv-platform/domain` straight to the domain package's `src`, which violated `rootDir` and had apparently never been typechecked. It now uses a standard TypeScript project reference to `../domain` and resolves the package normally through the workspace symlink and the domain package's built `dist`.
- Added `.prettierignore` and fixed `.gitignore` (added `dist` and `*.tsbuildinfo`); removed previously-committed `tsconfig.tsbuildinfo` build-cache files from git tracking.

## Milestone 3 Update

Status: Completed

Major deliverables completed (all under a new `packages/sdk` package, `@ctv-platform/sdk`):
- `ProviderInterface`: the exact contract from `specification/05-Provider-Architecture.md.txt` (`health`, `discover`, `search`, `movie`, `show`, `season`, `episode`, `streams`, `subtitles`), plus `supports(capability)` for the capability system.
- External DTO contracts (`dto.ts`): `ProviderMovieDto`, `ProviderShowDto`, `ProviderSeasonDto`, `ProviderEpisodeDto`, `ProviderStreamDto`, `ProviderSubtitleDto`, `ProviderCatalogItemDto`, `ProviderSearchResultDto`, `ProviderArtworkDto` — the fields these carry come directly from the "must extract" lists in `specification/06-Cinemana-Reverse-Engineering.md.txt`.
- `AbstractProvider`: a template-method base class handling capability gating, rate limiting, retries with authentication refresh, and structured logging uniformly, so a concrete provider only implements the `doHealth`/`doDiscover`/`doSearch`/`doMovie`/`doShow`/`doSeason`/`doEpisode`/`doStreams`/`doSubtitles` primitives.
- `ProviderError` + `ProviderErrorCodeEnum` (`TIMEOUT`, `UNAUTHORIZED`, `FORBIDDEN`, `NOT_FOUND`, `RATE_LIMITED`, `INVALID_RESPONSE`, `UNKNOWN_ERROR`, plus an SDK-level `NOT_SUPPORTED` for the capability gate) and `ProviderResult<T> = Result<T, ProviderError>`, reusing `@ctv-platform/domain`'s `Result`/`ok`/`err`/`DomainError` directly rather than re-inventing them.
- `ProviderStatusEnum` (`HEALTHY`, `UNAVAILABLE`, `MAINTENANCE`, `DISABLED`, `AUTHENTICATION_FAILED`, `RATE_LIMITED`, `UNKNOWN`) — deliberately mirrors the Prisma `ProviderStatusEnum` in `prisma/schema.prisma` value-for-value so a future persistence mapper needs no translation table.
- `ExponentialBackoffRetryPolicy` + `executeWithRetry`: implements the retry table from specs 05/06 (timeout/rate-limit/unauthorized/unknown retry; forbidden/not-found/invalid-response/not-supported do not), with authentication refresh triggered on `UNAUTHORIZED`.
- `FixedWindowRateLimiter`: per-provider request throttling with an explicit cooldown gate for `RATE_LIMITED` responses (both clock and sleep are injectable for deterministic tests).
- `AuthenticationStrategy` + `NoopAuthenticationStrategy`: authentication stays entirely inside the provider (Core/registry never manage it); the no-op strategy is a genuine, valid default for providers using a static API key rather than a login flow.
- `ProviderRegistry`: register/resolve by id, `registerFactory` for lazy/DI-friendly construction (a provider is only ever built once, on first `resolve()`, never manually with `new`), `list()` sorted by ascending priority, `listByCapability()`.
- `ProviderLifecycleManager`: drives Registered -> Health Check -> Available, producing a queryable `ProviderLifecycleSnapshot` (status/latency/message) per provider.
- `createProviderConfig()` (zod-validated `ProviderConfig`: timeout, user agent, rate-limit window, retry settings) — the SDK never reads `process.env` itself; a concrete provider's own package will read its own env vars and pass the resolved values in.
- 44 unit tests (`node --test`) covering every module above, including an end-to-end `AbstractProvider` test (via a minimal concrete `TestProvider`) exercising capability gating, retry-then-succeed, rate-limiter cooldown reporting, and authentication refresh together.
- `packages/sdk/README.md` documenting the package.

Architectural decisions validated:
- `@ctv-platform/sdk` depends only on `@ctv-platform/domain` (for `Result`/`ok`/`err`/`DomainError`/`MediaCategory`). It does **not** depend on `@ctv-platform/infrastructure` — per Architecture Decision 2, Providers are a sibling of Infrastructure (both sit in the Infrastructure Layer), not a consumer of it, so nothing in the provider framework can reach Prisma/Redis/BullMQ even transitively.
- The SDK defines its own minimal `ProviderLogger` port rather than importing infrastructure's `Logger`. Infrastructure's `ConsoleLogger` already satisfies this shape structurally, so no adapter is needed when a future composition root wires a concrete provider together; this avoids the wrong-direction dependency without duplicating meaningful logic (it's a 4-method interface, not an implementation).
- `packages/domain` and `packages/infrastructure` (Milestones 1 and 2) were **not modified** in this milestone — confirmed by `git diff --stat` showing changes confined to `packages/sdk/` and the specification files.
- "Dependency injection integration" for this milestone means the SDK's own classes are fully constructor-injected and never instantiate their dependencies internally by surprise (`ProviderRegistry.registerFactory` is the DI-friendly, lazy-construction path). Wiring a concrete provider into the app's actual `Container` (from `@ctv-platform/infrastructure`) is a composition-root concern that belongs to the milestone that introduces the first concrete provider (Cinemana), since no concrete provider exists yet to wire in.
- Only one concrete `AbstractProvider` base class was introduced (not several). A metadata-only provider (e.g. TMDB) is expected to simply omit `STREAMS`/`SUBTITLES`/etc. from its `ProviderMetadata.capabilities`; the capability gate then rejects those calls before the provider's own `doStreams`/`doSubtitles` ever runs.

Known gaps / accepted scope boundaries (documented, not hidden):
- No concrete provider (Cinemana or TMDB) exists yet — this milestone is exclusively the generic framework, matching the "Generic Provider Framework" deliverable in `specification/25-MILESTONES.md.txt`. Concrete providers are future work (Milestone 4 and/or a dedicated follow-up).
- The provider framework is not yet wired into any DI composition root or app entry point, since there is nothing concrete to register yet.

Tests and verification completed:
- `pnpm lint`, `pnpm typecheck`, `pnpm build`, and `pnpm test` all pass cleanly across the whole workspace (35 infrastructure tests + 44 new sdk tests).

Next recommended actions:
- Begin Milestone 4 (Import Pipeline): Discovery, Metadata, Streams, Subtitles, Matching, Validation, Publishing — the first place a concrete Cinemana provider (and likely TMDB) will be implemented against this framework and registered into a real `ProviderRegistry`.

## Milestone 4 Update

Status: Completed

Major deliverables completed (all under a new workspace member, `services/importer` / `@ctv-platform/importer`, added to `pnpm-workspace.yaml`'s `services/*` glob per `specification/02-Folder-Structure.md.txt`):

- **Discovery**: `DiscoveryEngine` runs Incremental (one page of "what's new" categories), Full (every category, fully paginated), Scheduled (same as Incremental, triggered on a timer), and Manual (same as Full, triggered on demand) discovery against any `ProviderInterface`, deduplicating items and tracking a per-provider checkpoint (`InMemoryDiscoveryCheckpointStore`, process-lifetime — see Known Gaps).
- **Import Pipeline**: `MovieImportOrchestrator` and `ShowImportOrchestrator` (dispatched by `ImportOrchestrator`) run the full per-item pipeline from `specification/08-Import-Pipeline.md.txt`: fetch -> duplicate check -> TMDB-style match -> metadata enrichment -> merge -> validate -> publish -> import media. `DiscoveryWorker`/`ImportWorker` consume two real queues (`ImportQueues`, built on `@ctv-platform/infrastructure`'s `QueueClient`) — Discovery Queue and Import Queue. `processInBatches` is a concurrency-limited worker-pool batch processor; `ProgressTracker` reports started/finished/stage/percentage.
- **Matching**: `ContentMatcher` implements the full priority chain from `specification/07-TMDB-Integration.md.txt` (IMDb id -> TMDB id -> exact original title+year -> exact title+year -> normalized Arabic title+year -> fuzzy match, a from-scratch Levenshtein-based similarity, threshold configurable). `MovieDuplicateDetector`/`ShowDuplicateDetector` answer a *different* question — whether this provider's content already exists in our DB, primarily via the `MovieProvider`/`TVShowProvider` join row (the schema's actual "Provider ID: Unique" duplicate-protection key), with TMDB id as a secondary cross-provider safety net. `CanonicalMovieResolver`/`CanonicalShowResolver` resolve to the canonical domain aggregate (existing or newly created, unsaved).
- **Metadata**: `MetadataEnricher` searches every registered `METADATA_ENRICHMENT`-capability provider and applies the same `ContentMatcher` to find the right entry before downloading full details. `mergeMovieMetadata`/`mergeShowMetadata` apply the "TMDB -> Provider" precedence for overview/artwork while leaving availability/streams/subtitles untouched (content-provider-owned, per spec). `validateMovieMetadata`/`validateShowMetadata` reuse the domain's own `Title`/`UrlValue` value-object validation rather than re-implementing it. `metadataNormalizer.ts` implements real Arabic text normalization (diacritics/tatweel stripping, alef/yaa/taa-marbuta unification).
- **Media**: `StreamImporter`/`SubtitleImporter`/`ArtworkImporter` validate then persist via new local Prisma-backed repositories (see Persistence below). `imageProcessor.ts` validates and selects artwork URLs (no pixel processing — that's Milestone 8/Sharp).
- **Validation**: `validateStream`/`validateSubtitle`/`validateMovieForPublish`/`validateShowForPublish`/`validateEpisodeForPublish` implement the exact rules from `specification/08-Import-Pipeline.md.txt` ("Validation Rules"), including "at least one valid stream" as a publish gate for movies/episodes.
- **Publishing**: `CatalogPublisher` reuses the domain's own `ContentDomainService.publishIfEligible`/`removeIfEligible` (Milestone 1) rather than re-implementing publish rules, then links the aggregate to its provider. `CacheInvalidator` reuses `CacheClient` (Milestone 2). `EventPublisher` reuses `EventBus`/`DomainEventDispatcher` (Milestone 1) to drain and dispatch an entity's pending domain events. `SearchIndexUpdater` publishes a real `ContentIndexUpdateRequestedEvent` via the same event bus — there is no search infrastructure yet (Milestone 8 scope), so this is honest working code for what the milestone can deliver, not a stand-in.
- **Operations**: `JobRetryPolicy` implements the job-level retry table from `specification/08-Import-Pipeline.md.txt` (timeout/network/rate-limit/provider/authentication retry with backoff; validation errors stop immediately). `DeadLetterQueue` holds exhausted/non-retryable jobs for inspection. `ImportMetrics` tracks the metrics named in the spec (imported movies/shows/episodes/streams/subtitles, failed, retried, average import time). `ImportLogger` enforces the required structured log fields (Import Job ID, Provider, Content Id, Stage, Duration, Status, Error) on top of `Logger` reused directly from `@ctv-platform/infrastructure`.
- **Persistence (new, local to this package)**: `Provider`, `MovieProvider`/`TVShowProvider`/`EpisodeProvider`, `Stream`, `Subtitle`, and `Image` were never modeled as domain aggregates or given repositories in Milestone 1/2 (out of that scope). `services/importer/src/persistence/` defines local ports and Prisma-backed adapters for them, following Milestone 2's exact mapper/repository conventions, so that neither `packages/domain` nor `packages/infrastructure` needed to change. Two schema-driven decisions: streams reconcile by `streamUrl` (no provider-side stream id column exists) and mark disappeared ones `isActive: false` rather than deleting; subtitles have no `isActive` column at all, so there is no deactivation concept for them.
- 118 unit/integration/pipeline tests (`node --test`), all against fakes/injected doubles (fake `ProviderInterface`, fake domain repositories, a fake Prisma client mirroring the infrastructure package's own test style, `InMemoryQueueClient` from `@ctv-platform/infrastructure`, injectable clocks/delays) — no network calls, no real database, per the project's testing rules. Includes true end-to-end pipeline tests (`orchestrator.movieImportOrchestrator.test.mjs`, `orchestrator.showImportOrchestrator.test.mjs`) exercising fetch -> match -> enrich -> validate -> publish -> media-import together.
- `services/importer/README.md` documenting the package, including every scope boundary below.

Architectural decisions validated:
- `@ctv-platform/importer` depends on `@ctv-platform/domain`, `@ctv-platform/infrastructure`, and `@ctv-platform/sdk` — it is the Application Layer (per Architecture Decision 2), sitting above all three, unlike `packages/infrastructure` and `packages/sdk` which each depend on domain only.
- Duplicate detection (does this item already exist in our DB) and TMDB-style matching (which metadata-provider entry corresponds to this content) are different questions answered by different mechanisms — conflating them was an early design mistake caught and corrected during this milestone's implementation.
- `packages/domain`, `packages/infrastructure`, and `packages/sdk` (Milestones 1–3) were **not modified** — confirmed via `git diff --stat`, changes are confined to `pnpm-workspace.yaml` (additive `services/*` glob) and `services/importer/`.

Known gaps / accepted scope boundaries (documented, not hidden):
- **Cast/crew/companies/countries/languages/collections** import (`specification/07-TMDB-Integration.md.txt`) requires domain aggregates Milestone 1 never modeled (`Person`, `Company`, `Genre`, `Collection`). Out of scope; only fields the `Movie`/`TVShow`/`Episode` aggregates can actually hold (title, overview, rating, runtime, trailer, artwork) are enriched.
- `ProviderMovieDto` (Milestone 3) has no rating/runtime/trailer fields — a DTO gap when applied to a metadata-enrichment provider. These flow through the same `raw` passthrough convention already used for `imdbId`/`tmdbId`.
- **Queue topology**: the specification names nine queues (Discovery, Movie, TV, Stream, Subtitle, TMDB, Artwork, Validation, Search). This implementation runs two real queues (Discovery, Import); every stage after discovery runs in-process within a single import job. Fanning out into the full nine-queue topology is a scaling optimization for Milestone 8, not a functional requirement.
- **Discovery checkpoints** are process-lifetime (in-memory); a durable adapter (e.g. backed by the `Setting` table) is reasonable future work requiring a new repository, out of scope for the reason above.
- **Image processing** validates/selects artwork URLs only; pixel-level resize/compress/convert (Sharp) is Milestone 8 scope.

Tests and verification completed:
- `pnpm lint`, `pnpm typecheck`, `pnpm build`, and `pnpm test` all pass cleanly across the whole workspace (35 infrastructure + 44 sdk + 118 importer = 197 tests).

Next recommended actions:
- Begin Milestone 5 (Backend API): Authentication, Search, Catalog, Favorites, Watch History, Continue Watching, Admin APIs — the first consumer of the domain repositories and (eventually) the importer's published content over a real REST surface.
- When a concrete Cinemana provider is eventually built (implementing `ProviderInterface` from `@ctv-platform/sdk`), register it into a real `ProviderRegistry` and wire `services/importer`'s queues/workers/scheduler into an actual running process (currently only exercised via tests).
